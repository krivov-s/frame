## Реализация системы безопасности
### Общие сведения
- Реализована ролевая модель и модель требвоаний Claims на объектах User / Role / UserClaim / RoleClaim
- Ограничения на чтение по типам объектов реализованы на уровне AppDbContext: получение всех DbSet-ов делается через 
специальный метод GetSet<T>(), который для текущего пользователя получает фильтры безопасности и сразу же 
добавляет их в возвращаемое IQuerable<T>, к которому можно потом добавить дополнительные фильтры.
- Метод ```DbSet<TEntity>.Set<TEntity>()``` переопределяется и блокируется, чтобы не было возможности получать сеты динамически.
- Контекст узнает о наличии моделей через их упоминании в методе OnModelCreating (файл AppDbContextModels):
```csharp
foreach (var type in EntityMetadata.GetAllEntitiesClassTypes())
{
    modelBuilder.Entity(type);
}
```
- Технологию EF GlobalQueryFilter не стал использовать, поскольку она сработает и на связанные данные, а в ряде случаев это не нужно,
и отследить это в runtime крайне тяжело. Например - построение выписки по клиенту, на которого пришел платеж от другого клиента,
и его имя не прочитаешь, поскольку прав нет: фигня получится. Этот пример конечно не для АХД и не для недвижки, но суть понятна.
- Аудит действий пользователя осуществляется на уровне AppDbContext: в таблицу Audit сохраняются все сведения о добавлении/изменении/удалении объектов.
- Логгирование осуществляется с использованием ILogger<>. Реализация с использованием SeriLog. Раздельные логи для безопасности, ошибок и приложения. 
Дополнительно - лог для SQL-запросов (на этапе разработки и отладки)
- Парсинг пользовательских фильтров реализуется с использованием библиотеки SmartFormat, которая позволяет в runtime осуществлять
динамический разбор строк формата ```"User.Id = {TestId}"``` (аналог интерполяции $"User.Id = {TestId}", которую нельзя делать динамически).
В фильтрах можно использовать системный и пользовательский список параметров, например: SystemParamList.SomeParam или UserParamList.AnotherParam.

> Использование Smart.Format нужно в основном для построения фильтров для запросов в методе ```IUserCore.ApplyReadQueryFilter()```.
Smart.Format позволяет получить текущие значения из AppCore и подставить их в запрос. 
>
> При этом в методах проверки безопасности на уровне типов и объектов при Add/Modify/Delete уже используется Expression, 
поэтому возможно реализовать кэширование (_в данный момент еще не реализовано_): скомпилированный Expression можно сохранять на уровне 
UserSession/SecurityProfile и переиспользовать каждый раз без повторного разбора и компиляции, поскольку AppCore каждый раз будет передаваться как аргумент
функции перед вызовом, все должно работать корректно.  
>

### Примеры фильтров в виде строки
- Пользователи, у которых есть UserClaims с заданными свойствами: ```UserClaims.Any(ClaimValue = "user@rshb.ru")```.
- Пользователи с заданными именами ролей: ```UsersRoles.Any(Role.Name == "Admin" || Role.Name == "Users")```


### Структура объектов безопасности:
#### UserServiceData  
Singleton, хранящий карту соответствия текущего пользователя и его объекта UserSession 
```csharp 
Dictionary<string, UserSession>
```
Предназначен только для хранения, с возможностью threadsafe доступа (с блокировками lock)

#### UserService
- Класс для доступа к синглтону UserServiceData.
- Если запрашиваемый пользователь в UserServiceData еще не существует - UserService считывает его из БД вместе со всеми ролями, 
создаст для него объект UserSession и сохранит в карте в UserServiceData для последующего переиспользования.
- Для избежания кольцевой ссылки UserLoader и RoleLoader обращаются к БД через NoSecurityDbContext - контекст, который 
ничего не знает про безопасность. _(кольцо возникает при создании AppDbContext: у него в конструкторе UserService, у которого в свою очередь 
в конструкторе UserLoader, которому тоже нужен контекст)_
#### UserSession
Сессия пользователя. Хранит карту прав доступа пользователя к отдельным типам системы 
```csharp 
Dictionary<string, SecurityProfile>
```
- Карта формируется из набора ролей пользователя и объектов TEntityRights, привязанным к конкретным ролям путем 
суммирования прав для одинаковых типов через "OR". Объединение записывается в объект SecurityProfile.
- Если пользователю не нужно ставить ограничения на конкретный тип - объект SecirutyProfile не должен существовать.
- При построении карты проходимся по всем типам из Domain, если есть тот тип для кого SecirityProfile не был
создан - считаем что на него есть все права, и создаем новый SecirityProfile, у которого все прова проставляем "1=1".
Это нужно, поскольку права суммируются по OR. Это значит, что если роль админа, в которой нет ограничений, 
просуммировать с юзером, то будет просто наложено ограничение на админа, т.е. условный результат 
будет () or (filter) что равнозначнорезультату просто (filter). Поэтому мы делаем чтобы было так: (1=1) or (filter)
#### SecurityProfile
- Профиль безопасности конкретного типа. Составляется из набора фильтров.
- Если у пользователя несколько ролей с различными настройками фильтров для одного типа, фильтры объединяются через OR.

### Страница /checkinstance
В интерфейсе пользователя реализована служебная страница по адресу /checkinstance, которая позволяет удалить/создать 
базу данных и осуществить ее первичное наполнение.

### Keycloak notes
#### 1. Аутентификация одним запросом с указанием и клиента и пользователя.
##### 1.1. Настройка клиента в keycloak
- Client authentication = On
- Direct access grants = On. Этого достаточно чтобы аутентифицироваться сразу, без предварительного запроса клиентского токена.
##### 1.2. Пример http запроса
- POST http://sbox:8282/realms/ccps/protocol/openid-connect/token
- Headers: Content-Type:application/json
- Body: 
  ```
  client_id:ccps-frontend
  grant_type:password
  username:______
  password:______
  client_secret:
  ```
#### 2. Аутентификация только клиента, без пользователя.
##### 2.1. Настройка клиента в keycloak
- Client authentication = On
- Service accounts roles = True. Этого достаточно чтобы аутентифицироваться сразу, без предварительного запроса клиентского токена.
- Keycloak автоматически создает системную учетку с именем service-account-client-id, в нашем примере получится **service-account-ccps-backend** 
##### 2.2. Пример http запроса
- POST http://sbox:8282/realms/ccps/protocol/openid-connect/token
- Headers: Content-Type:application/json
- Body:
```
client_id:ccps-backend
grant_type:client_credentials
client_secret:
```

#### 3. Этапная аутентификация, сначала клиента, потом пользователей
Теоретически должно быть так: получаешь токен клиента, и его используешь для получения токенов пользователей.
